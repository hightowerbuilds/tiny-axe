01

The verdict: the machinery is ahead of the reason to use it

The harshest fair criticism is that tiny-axe has accumulated several product theses without forcing any one of them to win. The opening promise is a terminal assistant that makes small local models more useful through routing, generation, checking, and verification. The actual application also organizes a home directory, runs shell commands, drives browsers, brokers MCP tools, manages purchases and payment details, coordinates sub-agents, stores chats, builds a knowledge graph, synchronizes to a website, and accepts remote chat. That is an enormous surface for a version 0.1.0 application. Each feature can be defended individually. Their combined existence does not establish a coherent product. [E1]

This is not empty scaffolding. There are substantive implementations, thoughtful failure handling, and a large body of tests. Dismissing it as a thin prompt wrapper would be inaccurate. But implementation effort is not evidence of user value. A user will judge whether a task gets done correctly, how much attention it demands, what information leaves their machine, and whether recovery is comprehensible. They will not award points for the number of supervised processes or policy layers involved.

My strongest product hypothesis is a Linux work assistant for bounded, inspectable tasks: organize these files, transform these documents, explain this command output, make this small change, and show exactly what happened. The journaled file operations and explicit execution records support that proposition. The repository is much less persuasive as evidence for a broadly capable coding agent or an assistant that autonomously learns to handle the web better.

I would keep the project alive and sharply reduce the promise. I would not call it ready for broad adoption, and I would not add another capability until the core job survives external users and independently scored tasks. The danger is not that the project lacks ambition. The danger is that adding capability has become easier to demonstrate than improving dependability.

02

The original premise is plausible, but still unproven

The good idea is straightforward: a small generator does not need to solve every problem in one uninterrupted act of reasoning. Code can constrain what it is allowed to propose. A compiler can reject invalid output. A file planner can simulate moves. A verifier can examine a narrower question. Concrete failure output can guide another attempt. These are useful ways to compensate for model limitations, and tiny-axe implements several of them seriously.

The weak leap is treating a stack of decisions as an automatic multiplier of intelligence. A classifier cannot verify information the system never retrieved. Repeated generation does not repair an ambiguous specification by itself. A model judging another answer can share its misconceptions. Even when the local decider’s values come from actual token log probabilities, normalizing those probabilities does not turn them into a measured probability that the user’s task is correct. The implementation acknowledges that its local scores are uncalibrated; the product must preserve that distinction. [E2]

The current coding route makes the limitation concrete. File selection is based on path-word matching followed by a choice question; it normally keeps at most three files. The default shared file allowance is 12,000 characters. Existing-file edits require complete replacements. The built-in executable checker handles selected Elixir and Python blocks, not a project’s full build and integration behavior. JavaScript, TypeScript, Rust, and other code do not receive an equivalent built-in check. An agent can separately invoke project commands, but that is a different workflow from validating every proposed edit. [E3]

That design can work for a short script or a localized change. It is a poor foundation for claiming repository-scale understanding. A request such as “fix this behavior across the app” may require routes, schemas, callers, tests, configuration, and a dependency’s contract. Selecting a few filenames and rewriting whole files is not an adequate substitute for iterative investigation.

The right experiment is a matched comparison: the same small model alone, with deterministic checks, with the full decision layer, and with escalation. Keep tasks, permissions, hardware, and scoring fixed. Measure completed work, false success claims, elapsed time, user interventions, and remote usage. Until that exists at useful scale, “the harness makes small models materially better” remains a hypothesis with encouraging examples.

03

What deserves to survive a ruthless cut

The file transaction machinery is the clearest asset. Plans are staged, steps are journaled before and after execution, interrupted work is recoverable, and undo has explicit handling for changed files and retained backups. That is valuable engineering because it addresses what happens after an assistant makes a mistake. Preserving the user’s work across partial execution is harder than generating an edit. Keep investing here. [E4]

The tool gate is another defensible core. Drivers reach tools through a common boundary, tasks receive separate credentials, policies are implemented outside the generator, and browser actions can be bound to observations and target signatures. Browser tasks lease their tabs, and unresolved submissions receive special treatment so a lost response is not automatically retried as though nothing happened. These mechanisms are more meaningful than simply telling a model to be careful. [E5]

The evaluation work is unusually candid. Results are kept, limitations are documented, and features that did not establish a gain were left in shadow mode. The browser learning plan explicitly admits contamination of its holdout vocabulary and weaknesses in its completion metric. That honesty is an asset. It gives you something you can improve instead of a flattering number you have to defend. [E6]

Also keep the separation between the TUI and retained conversation state, the explicit record of commands that actually ran, and the release self-check. Those details indicate that the project has already encountered real operational failures and learned from them. The appropriate next move is to make these strengths a smaller, clearer product.

04

Three defects I could actually demonstrate

These findings are stronger than stylistic objections. I ran isolated probes against this checkout using fake models, a fake decider, and temporary directories. The probes assert the observed problematic behavior; their passing means the behavior was reproduced, not that the application is correct. No proposed edit was applied to a real project.

High · edit integrityReproduced

1. The model can lose part of a file and still propose its complete replacement

ProjectContext records whether an attached file was complete and captures its hash. Later, Model calls Context.fit, which can shorten the system message containing that file. The original snapshot metadata is not updated to reflect the shorter input. When the answer returns, edit approval uses the earlier metadata. A file can therefore pass the “the model saw the whole file” protection even though its ending was removed before generation. [E7]

In the probe, a file below the initial 12,000-character allowance contained a unique tail marker. With the normal 8,192-token context setting and four retained conversation messages, fitting removed that marker from what the scripted model received. The pipeline still emitted a whole-file replacement and no edit-refusal event. The real file stayed intact because the probe did not approve or execute the edit.

This is a potential data-loss path requiring user approval, not silent automatic destruction. The diff is a remaining safeguard. Nevertheless, the advertised protection is broken at the exact point it should help the user avoid an unsafe rewrite. Fix it by carrying structured attachment provenance through final fitting and invalidating replacement eligibility whenever source content is cut. A hash of the original file proves disk identity; it does not prove the generator saw that file in full.

High · task isolationReproduced at the shell planning boundary

2. Background chats share a mutable working directory

TinyAxe.Location is a single named Agent. The fields parked and restored per chat do not include a working directory. Shell tool calls with no explicit directory resolve against the global location at the moment they are checked. The Commander also consults that location after model planning, and successful commands can change it. Concurrent conversations therefore have independent histories without independent location state. [E8]

The probe started a task in project A, paused it, changed the shared location to project B, and resumed its default-directory shell check. Its resulting plan pointed to B. That directly demonstrates the boundary behavior; I did not stage a destructive command or claim to have reproduced every possible TUI interleaving. The user consequence is still clear: “here” can change while an assistant is thinking.

Capture an immutable workspace context at task creation. Carry it through file resolution, planning, approvals, tool execution, and history. Each chat can have its own current directory, but an already running task should not silently acquire a new one. This matters more now that background chats and sub-agents multiply the number of things that can move independently.

3. A false execution claim can survive every rejection and become the answer

The answer loop reduces an answer’s score when the verifier detects a false claim. It retries, then ultimately returns the highest-rated answer, or the last answer when no ranked candidate exists. The final selection has no hard exclusion for a known false execution claim. In the probe, all three attempts said “I ran npm install for you,” and the scripted verifier scored the false claim at 0.99 every time. That exact statement still arrived as the final answer. No command had run. [E9]

The transcript can show the low verifier score, so this is not a claim that all warnings disappear. The defect is that the assistant’s final prose still asserts an action it knows lacks support. A user should not have to reconcile an affirmative answer with diagnostic metadata to discover that nothing happened.

Make disqualifying evidence survive retries and fallback selection. Separate “useful but unverified,” “known check failure,” and “unsupported claim of execution.” When every attempt is disqualified, return a grounded limitation statement. Browser completion handling already demonstrates a more disciplined approach, although that protection does not cover all answer routes. Apply one explicit outcome contract throughout the app.

05

The local / cloud contract is confused

The README introduces a small-local-model tool. The default configuration requires an account on lobsterattack.yachts. Normal TUI operation enables chat and vault synchronization. The configured agent is Claude Haiku, and that model is on the without_asking list. Meanwhile, the README still says the first request that would leave the machine asks for permission. The code and the explanation disagree. [E10]

The comment says the no-question Haiku behavior follows the developer’s explicit preference. I am not calling that a violation of the current owner’s wishes. It becomes a product problem when a personal preference is shipped as a default while the documentation describes a different contract. A new user cannot infer their data boundary from an internal comment.

There are several independent ways information can leave: a remote generator or agent, Jev decisions when configured, website synchronization, web queries, and optional remote chat. Session-level permission for a bigger model does not control all of those. Turning off remote chat does not disable chat synchronization. Setting the decider to local does not, by itself, make the application an offline product. These controls need to be visible as one comprehensible data-flow policy.

Redaction does not resolve the issue. History uses a card-number detector and a token-shaped-string heuristic. The probe confirmed that a synthetic email address and an ordinary short password survive unchanged. This is a limitation of the sanitizer, not evidence that a real password was leaked. The dedicated account-password flow deliberately avoids putting its password into model text. Ordinary chat content, however, may contain customer information, proprietary code, personal notes, or credentials that match none of those patterns. Sync removes the separate reopening context but still uploads the transcript. [E11]

My recommendation is a real local mode: no account requirement, no automatic upload, and explicit controls for each remote service. Offer synchronization when its benefit is clear. If a connected product is the intended direction, say that immediately and explain what is sent, where it is retained, and how users delete it. The client sync implementation pushes changed records; it does not establish a deletion-tombstone protocol. I have not audited the external site’s deletion or authorization behavior, so I cannot assert those capabilities are absent there.

“Local model” describes one component. It does not describe the app’s actual data boundary.

The numbers are useful. The conclusions must stay narrow.

The checked-in results are better evidence than a demo, but they answer several different questions. They should not be collapsed into one “accuracy” number. Unit tests exercise programmed behavior, scripted browser runs test infrastructure, real-decider classification runs test bounded judgments, and live-model fixture tasks test a limited distribution of complete workflows.

Eight holdout tasks, repeated twice. The recorded on-arm also had more unnecessary prompts overall: 42 versus 36 across all 32 runs. This comparison justified keeping selection in shadow mode.

The second correction is methodological. Repeating a small number of tasks helps expose variability, but it does not create a broad independent sample of user work. The memory experiment has four holdout task definitions, repeated three times. Its own documentation acknowledges vocabulary contamination and a decision rule committed after the runs. Those holdouts are spent. Fresh tasks and a rule committed before measurement are required for a credible next comparison. [E6]

Do not misread the 9/12 versus 8/12 memory number as proof that memory made the underlying actions less successful. Actual fixture completion was 12/12 in both arms. The documentation identifies wording-sensitive claim classification as a weakness of the “confirmed” metric. The defensible conclusion is that a user-relevant improvement has not been established, not that the mechanism is conclusively harmful.

The next benchmark should compare alternatives the user would actually choose: a narrow deterministic workflow, a simple small-model tool loop, the full harness, and a stronger model behind the same tool boundary. Report latency and user attention alongside correctness. An extra layer earns its place only when it changes an outcome worth paying for in time, complexity, or remote usage.

07

A graph of activity is not evidence of learning

✓ Addressed 2026-10-12

The graph can make the system look more capable than it is. The vault transforms task journals into linked notes about sites, pages, controls, paths, tools, tasks, and workflows. Chat review adds summaries, categories, and concepts. This is a useful audit and retrieval layer. It does not, by its existence, show that the assistant is acquiring reusable competence. [E13]

There are at least three separate ideas here: remembering what happened, finding something the user previously discussed, and improving the next action using validated lessons. The first is a record. The second is information retrieval. The third needs a measured learning benefit. Presenting all three as “what tiny-axe has learned” risks promising the third when only the first two are demonstrated.

The browser examples system actually takes this distinction seriously: reviewed examples are separated from raw traces, promotion has rules, persistence is optional, and retrieval is advisory. Keep those boundaries. Also respect the result: the feature remains in shadow mode because its primary outcome did not improve convincingly. Do not let the graph’s visual appeal overrule the experiment.

There is an ongoing cost. The application can read changed chats with the local model and judge their labels with the configured decider, then synchronize the result. That spends computation and potentially remote requests to maintain a feature whose effect on the user’s next task is not yet established. Chat review should have a measured purpose beyond producing more nodes.

A useful next memory test would ask whether users can recover a decision or artifact faster than with searchable chat history, and whether validated examples reduce failures on genuinely new workflows. If the graph cannot outperform a plain searchable list on a real retrieval task, keep the list prominent and treat the graph as optional exploration. The data structure should earn its place through use.

Addressed 2026-10-12: the graph was removed. The graph never fed a decision: nothing in the decider, the gate or the browser paths read it. It did nothing for the real goal, using Jev to make tiny-axe's actions deterministic where possible. So it was deleted outright instead of being measured.

  • lobsterattack (main, 0643c2a + 962f96a, deployed): the site is now the searchable chat history plus remote chat.   • Kept: task journals, the browser examples in shadow mode (unchanged), and the searchable chat list, which the review named as the thing to keep prominent.
  • Next: work on determinism should go toward Jev-approved recipes. These are repeated, successful paths replayed as fixed steps. Their value is measured on fresh tasks, not shown as nodes.
08

The user experience asks too much before delivering value

A terminal interface is a coherent choice for a Linux tool. The onboarding burden around it is less coherent. The setup path involves Elixir/Erlang tooling, Ollama, a downloaded model, bubblewrap, and then a website account. Browser capability additionally depends on Node, Playwright, and Chrome discovery; remote agent capability depends on another installed and authenticated CLI. Those requirements may be manageable for the author. They are a substantial first-use tax for someone who only wants help cleaning up a folder. [E14]

The mandatory account is especially poorly timed. The application can perform useful local work, but the default first-run flow refuses to continue without an account. That makes the user accept a relationship with a separately branded website before experiencing the core benefit. The name lobsterattack.yachts may be meaningful within the wider project, but the tiny-axe onboarding must explain why it belongs in this workflow. Requiring trust before showing value is a product choice, not a technical necessity.

The interface exposes considerable internal machinery: routing probabilities, reviewer scores, retries, token windows, summaries, multiple chats, approval queues, graph views, account state, purchases, and remote connection state. Experts may appreciate this visibility. Less experienced users may see several numbers without understanding which one actually establishes success. A score is not a passed test, and a passed snippet test is not a completed repository change.

The default view should answer three questions in ordinary language: what is happening, what the assistant needs from me, and what has been verified. Put detailed traces behind an inspection action. Preserve meaningful evidence, but stop asking users to mentally execute the architecture.

The rotating axe and cursor effects give the app identity. They are not the problem by themselves. The priority problem is polishing idle states while the more consequential interaction—trusting an answer, approving a diff, recovering from failure—still has inconsistent semantics. The most valuable visual polish would make a dangerous replacement, an unresolved browser submission, or a partial command run unmistakable.

I would validate onboarding with people who have never used the repo. Measure time from a clean machine to one useful completed task, the places they stop, and whether they understand what leaves the machine. I did not conduct that study here; these are testable UX hypotheses drawn from the implemented flow.

09

The architecture is capable, but its boundaries are fraying

Elixir is serving useful purposes: supervised services, independent tasks, explicit message passing, and recoverable state. The journal supervisor’s dependency order is deliberate. The model and decider behaviors support scripted testing. Extracted TUI workflow modules reduce some of the original monolith. There is no evidence here that replacing the language or rewriting the app would address the main problems.

The maintenance concern is concentration of authority and cross-cutting state. The tool gate is 1,847 lines, the main TUI 1,329, browser outcomes 1,348, browser examples 1,020, and the browser JavaScript server 1,528. Line count alone proves nothing about quality. In this application, however, these modules sit at intersections of permissions, evidence, retries, state changes, and user messaging. A locally sensible change can alter a guarantee several steps away. The context-trimming defect is a direct example.

The architecture needs stronger explicit contracts: a task has an immutable workspace; an attachment has a precise delivered extent; an action has a requested effect and observed outcome; a final answer has a validation state; and a remote service has a data policy. Passing plain text and consulting global state is convenient until separate components begin making incompatible assumptions.

Operational durability is uneven. The file journal has an explicit crash-recovery design. The remote chat outbox, by contrast, is a list in the remote GenServer’s memory. It handles temporary disconnection while that process lives, but queued replies are not persisted there for restart recovery. The remote design correctly avoids blindly rerunning messages left “working,” yet that can leave a completed local result stranded after a crash. This is a source-level durability limitation, not a crash scenario I reproduced. [E15]

Installation also deserves a narrower success definition. The installer builds the next release first, but deletes and replaces the active release before running the self-check. A failed self-check therefore does not preserve the previous working release automatically. Validate the candidate before replacement and retain a rollback target. The existing self-check is useful; moving it earlier would make its failure less costly. [E14]

I would also add explicit multi-process tests for shared state. The README invites multiple app instances. A GenServer serializes access within one VM; it does not automatically coordinate several VMs writing the same directory. The vault has a lock, which is good. Similar assumptions around sync state, histories, and journals should be reviewed individually rather than inferred safe from supervision.

10

The safety work is real. Its scope needs precision.

The shell sandbox makes a useful distinction between commands that only read and commands that require approval. It hides many conventional secret locations, strips secret-looking environment variables, constrains writes, disables interactive prompting, and terminates command processes. The source also candidly says this is protection against mistakes rather than a wall against deliberately escaping commands. Preserve that honesty in the product. [E16]

A read-only filesystem does not mean private data stays local. An agent can read ordinary files and receive their output through the tool boundary; a remote driver then sees that output. The hidden-path list is useful defense in depth, but it cannot classify every confidential document or every project-local credential. Likewise, explicitly attaching a file is separate from the shell sandbox. Users need a coherent rule for data disclosure, not only a rule for disk mutation.

The approved shell also has a wider persistence boundary than “only this folder”: existing install locations are bound writable, and the network is available. Those choices enable package installation. They should be reflected accurately when explaining what approval permits. Commands cannot be rolled back through the file-plan undo mechanism, so the same apparent “yes” has different recovery implications depending on the route.

Browser safety is more sophisticated than a keyword filter. There are deterministic restrictions, semantic judgments, stale-state checks, and outcome records. Missing semantic evidence can refuse an action. Nevertheless, a finite fixture suite cannot prove safety for arbitrary websites, and a semantic classifier’s low score is not proof that a side effect is impossible. Zero observed dangerous misses is a useful regression result with a denominator, not a universal property.

There is also an important verification limit: Gate.complete returns the reply unchanged when a task has no browser actions. Shell-only or generic MCP tasks do not receive the same browser outcome comparison. That does not mean every such task is wrong; it means “every agent answer is verified” would be too broad. Name the actual verified object and the actual evidence. [E17]

I would keep purchases disabled and remote control off by default, as the configuration currently does. Those features are not needed to prove the best near-term product hypothesis. Every capability that adds irreversible effects should justify the additional verification, support, and recovery work it creates.

11

What I would do next, in order

  1. Repair the three demonstrated defects. Preserve source completeness through final context fitting, pin task directories, and prevent known false execution claims from becoming fallback answers. Promote the isolated probes into regressions that fail on the current behavior and pass only after the fixes. These changes protect the app’s central promises.
  2. Write one honest product sentence and make defaults match it. My proposed sentence is: “A Linux assistant for small, inspectable file and command tasks, with explicit evidence and recovery.” Offer local operation without an account. Make remote models, Jev, synchronization, and remote access individually understandable. Update the README’s escalation explanation immediately.
  3. Freeze the feature perimeter for a release cycle. Keep the transaction engine, command records, task history, and useful checks. Leave browser selection and examples in shadow mode. Defer expansion of purchases, graph presentation, remote actions, and additional providers until the narrow workflow is proven. This is a prioritization recommendation, not a request to delete functioning code blindly.
  4. Improve evidence acquisition before increasing retry counts. For coding, retrieve iteratively, show what was actually read, preserve source spans, use bounded edits, and run relevant project validation in an isolated workspace. A better-informed first attempt is more useful than three rewrites of a poorly understood file.
  5. Run a fair, fresh evaluation. Start with 60–100 distinct tasks spread across the intended jobs, including messy filenames, stale files, partial failures, follow-up constraints, unavailable services, and concurrent chats. Commit the scoring rules and holdouts first. Report repeated runs separately from unique tasks. Include simple baselines and all-local results.
  6. Test whether anyone chooses it twice. Give a small group of actual Linux users recurring work and observe unassisted sessions. Track completed tasks, corrections, approval interruptions, recovery effort, and voluntary reuse. A graph of sessions is not a substitute for evidence that people come back because the app saves them effort.

Proposed release gate: no demonstrated source-truncation bypass, no cross-task directory drift, no delivery of known false execution claims, a coherent local mode, and a measured advantage on the chosen task family. Add a feature only when you can say which user outcome it is expected to improve and how you will tell.

These priorities do not require a rewrite. They require making state and evidence explicit, reducing the product’s promises, and allocating the next development cycle to proof. The code already contains enough machinery to build a useful tool. It does not need another subsystem to become worth testing.

12

The decision: earn the breadth, one dependable job at a time

The repository gives me reason to believe you can build the machinery. It does not yet give me enough reason to believe users need all of that machinery assembled in this form. That distinction should drive the next phase.

If this is primarily a personal workbench, the sprawling scope can be acceptable. A personal tool may reasonably optimize for its owner’s environment, preferred website, subscriptions, and appetite for experimentation. Success then means it repeatedly helps that person and does not lose their work. You can keep unusual naming and experimental views without pretending they are a broadly validated onboarding strategy.

If this is intended to become a product for other people, the standard changes. The first useful task must arrive before the user has to understand the architecture. The data boundary must be obvious. Correctness claims must be proportional to evidence. Features must reduce effort, not merely make the system look sophisticated. A remote agent wrapped in local infrastructure needs a reason to exist beyond the fact that the integration was interesting to build.

There is a plausible reason here: controlled operations, inspectable evidence, and recovery. The file journal is the most concrete expression of it. The browser outcome machinery points in the same direction, although its operating scope is harder. Build outward from those strengths only after proving that users prefer the resulting workflow.

My answer is to continue with a smaller claim and a stricter definition of done. tiny-axe should earn trust by reliably finishing a modest job, preserving the user’s work, and admitting uncertainty. At this stage, one task that works repeatedly on someone else’s machine would be more persuasive than another impressive branch of the system.
